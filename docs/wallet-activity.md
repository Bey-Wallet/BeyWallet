# Wallet activity History

History now combines payments with named wallet maintenance. The filters include **Payments** and
**Wallet maintenance**; existing payment rail, date and mint filters remain available. Sent/Received
filters exclude maintenance. Pending includes unresolved maintenance.

| Operation                                                       | History behavior                                                                        | Amount and authority                                                                                                                                                                           |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Get change                                                      | One entry projected from its existing submitted/completed journal                       | Confirmed fee and negative balance change only after the journal commits completion. Submitted outcomes need review. Prepared/cancelled previews stay quiet.                                   |
| Optimize                                                        | One durable summary for each new optimization, grouping exact internal send/receive IDs | Completion follows successful receive. Interrupted outcomes need review. Fees and net balance change remain unavailable because global before/after totals can include unrelated activity.     |
| Recovery/import scan                                            | One summary per user-selected recovery batch; retries update that batch                 | Partial/interrupted recovery needs review. Observed balances include existing funds and are never represented as received income. Startup restoration does not create a payment receipt storm. |
| Reclaim                                                         | Original payment remains the receipt; refunded rows read Funds reclaimed                | Uses existing saved payment state, rather than inventing a second incoming payment.                                                                                                            |
| Transfers, ecash, Lightning, Bitcoin, NFC/Nostr payments        | Existing authoritative payment History                                                  | Existing payment execution, receipt validation and transfer grouping are retained.                                                                                                             |
| Proof inspection, spent-proof cleanup, toggles, balance refresh | Intentionally quiet                                                                     | These do not establish a new money movement. No fabricated payment or maintenance receipt.                                                                                                     |

Completed maintenance opens the same compact receipt sheet pattern, using outlined ListTables and
collapsed technical IDs. Unresolved maintenance opens a full screen review. Review actions only
navigate to the existing operation; they never resubmit a payment. Missing optimization receipts
offer a safe Proofs fallback.

Removing a settled activity adds a local History tombstone. It does not delete spendable proofs,
recovery journals or the internal grouping links. Wallet deletion removes these wallet database
tables with the rest of the wallet. Activity summaries contain allowlisted public fields, never
tokens, proof secrets, invoices, keys or recovery material. No notification or outcome haptic is
generated by reading, reconciling or displaying maintenance History.

## Existing data and limits

- Existing submitted/completed Get change journals can appear immediately. Other old optimizations
  cannot reliably be inferred from equal amounts or nearby timestamps and are not reconstructed.
- Optimization receipt linking uses the existing exact token/receipt verifier. When a verified local
  receipt has not been saved yet, its receive row can remain separate until History refreshes and the
  exact link is available. Unknown outcomes never become success merely because a balance changed.
- Recovery summaries start with batches run on this version. A still-existing interrupted batch can
  refresh its summary from its saved session. No historical income is invented from restored balances.
- This remains a recent activity feed, with the existing payment query window and recent maintenance
  records; this change does not add infinite scrolling or an accounting export.
- Summary persistence is best effort and must not change a wallet operation's result if storage fails.
  Operational journals, proofs and core payment records remain authoritative.

## Manual device checklist

Use a preview/development build with these changes, a test wallet and small amounts at a mint you
control or trust. Reload from `yarn start:low-memory` if using the existing development build.
These checks remain **unverified on Android and iOS devices** in this workspace.

1. Open **Settings → Wallet → Get change** (or the current Wallet settings group). Complete one
   operation, then open **History**. Expect one **Change prepared** row, its confirmed fee and balance
   decrease. Check **Show details**, close, reopen and restart Bey: no duplicates or payment alerts.
2. From the existing Optimize screen, optimize a mint with enough proofs to enable its action.
   Expect one **Wallet optimized** row, not two send/receive rows once the exact receipt is saved.
   Fee/balance change must say **Unavailable**, never a guessed fee or a positive incoming payment.
   Make an unrelated equal-value payment and verify it remains separate.
3. Test **Filters → Wallet maintenance**, **Payments**, the mint filter, and **Sent/Received**.
   Maintenance must not appear under Sent/Received. Recovery involving several mints should match
   each participating mint filter.
4. Open a completed maintenance row: expect one compact bottom sheet with outlined tables. Close
   using X, swipe, or Android Back. Reopen with large text, VoiceOver/TalkBack and both themes; check
   readable wrapping, full-width separators, labels and touch targets.
5. Use a controlled test environment to interrupt an Optimize after submission. Do not blindly
   repeat it. Expect a pending/review entry; **Review operation** opens its saved payment or offers
   Proofs when unavailable. Merely opening History must not send, receive, reclaim or retry funds.
6. Run a manual recovery batch. Expect one recovery summary. Force one selected test mint offline:
   the summary must need review, count completed mints accurately, and label its balance as observed.
   Restart during recovery and inspect again. Retry only through the existing recovery screen; the
   same batch should update rather than add another income entry.
7. Reclaim an eligible unclaimed ecash payment through its existing flow. Verify its original row
   reflects the saved result as **Funds reclaimed**, with no extra fake incoming receipt.
8. Remove a completed maintenance entry, confirm the dialog, then restart. It stays hidden, internal
   Optimize legs do not reappear, and wallet balance/proofs remain intact. Pending/review records
   offer review instead of removal. Cancel the dialog and verify nothing changes.
9. Lock/unlock, switch wallets if supported, and delete only a disposable test wallet. Old maintenance
   receipts must not become visible in another wallet. Opening History must create no extra toast,
   OS receipt or outcome vibration.

Automated validation results are recorded with this change's delivery notes. Real mint execution,
native sheet gestures, device authentication and accessibility still require the checks above.
